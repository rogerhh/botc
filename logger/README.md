# Logger Design

The logger is the engine's memory of the game. It exists for three reasons:

1. **End-of-game narration.** When the game ends, the Storyteller wants to
   walk the table through what actually happened, night by night, in order.
2. **Mid-game audit.** During the game, the Storyteller (and curious
   players, after death) sometimes need to ask "wait, what just changed?"
   or "why is Charlie poisoned?". The logger answers that.
3. **Undo and replay.** A misclick, a misheard player, a wrong arbitration
   — the Storyteller needs to rewind a step. After the game is over, a
   stored log plus the seating order and the Storyteller's decisions should
   reproduce the game deterministically for debugging and post-mortems.

The logger is a passive subsystem. It does not decide anything. The engine
emits Events; the logger records the ones that matter and renders them on
demand.


## Where it sits

The logger is a separate top-level module. It does not import from `ui/`,
and the engine depends on it through a thin interface (`EventLog.append`).
The UI depends on it as a read-only data source for the timeline panel and
the end-of-game replay.

```
logger/
  event_log.py     EventLog: ordered record of state-changing events
  entry.py         LogEntry: one row in the log
  sinks.py         Output destinations (memory / JSONL / UI stream)
  renderer.py      Event -> human-readable summary
  replay.py        Reconstruct game state from a stored log
  snapshot.py      Periodic state snapshots, used by rewind
```


## Goals

- **Record every Event that changed game state**, in the order the engine
  processed it.
- **Skip non-state-changing events** (CheckCondition that found the
  condition false; Wakeup events whose ability resolved to no information
  and no effect — though Wakeup is still recorded if it was visible to a
  player, see "What gets logged" below).
- **Be the single source of truth** for "what happened in this game". The
  UI's timeline panel, the end-of-game transcript, and any rewind operation
  all read from the same log.
- **Survive a crash.** A live game can run a long time. The log is
  durable to disk via the JSONL sink, so a process restart does not lose
  the record.
- **Be private.** The log contains Storyteller-level information (drunk
  player saw fake info X; Imp killed Y) and is never sent to a player's
  phone.
- **Be deterministic.** Given the same seating, character assignment, and
  Storyteller decisions, replaying the log reconstructs the same game
  state.


## Core Concepts

### LogEntry

A `LogEntry` is one row in the log. It carries:

- `index` — monotonically increasing integer, starting at 0. The first
  entry is always the Setup event.
- `timestamp` — wall-clock time the engine processed the event. Useful
  for replay timing and debug.
- `phase` — the game phase at the moment the event was processed
  (`SETUP`, `FIRST_NIGHT`, `NIGHT_n`, `DAY_n`, `FINISHED`). Stored on
  every entry so the renderer doesn't have to scan back to find the
  current phase.
- `event` — the structured `Event` itself: type, source, targets,
  payload. This is the machine-readable record.
- `summary` — a short human-readable sentence for the Storyteller's
  timeline UI ("Imp chose Bob; Bob died.", "Empath learned 1.").
  Generated by the renderer at append time so the UI never has to format
  it again.
- `visibility` — `STORYTELLER` (most rows) or `PUBLIC` (rows that the
  table at large knows happened, e.g. executions, day deaths). Drives
  what gets shown in the public-facing recap if we ever produce one.

Entries are immutable once written. Editing a row means appending a
correction event, never mutating the original.


### EventLog

`EventLog` is an append-only ordered list of `LogEntry`s. The engine
holds one reference to it. Its API is small:

- `append(event, *, phase, visibility) -> LogEntry`
  Wrap the event in a LogEntry, run the renderer, push to all sinks,
  return the entry.
- `entries(*, since=None, until=None, phase=None, visibility=None)`
  Filtered iteration for the UI timeline panel.
- `last() -> LogEntry`
- `len()`
- `truncate_after(index)` — used by rewind. Drops everything after the
  given index. The actual game-state revert is done by the snapshot
  layer; the log's job here is just to pop the now-invalidated entries
  and notify sinks.

`EventLog` does not enforce what should and should not be logged. That
decision is made by the engine before it calls `append`. See "What gets
logged" below.


### Sinks

A sink is an output destination for log entries. Sinks are pluggable so
the same log can be written to memory, persisted to disk, and streamed
to the UI without the engine knowing the difference.

- **InMemorySink** — the default. Holds the entries in a list. Required
  for filtered queries and for the renderer to look back across entries.
- **JsonlSink** — appends each entry as one JSON line to a file on
  disk. Crash-safe: the file is fsynced after each line. Replay reads
  this file back.
- **StreamSink** — pushes new entries over the engine -> Local UI
  socket. The UI's timeline panel renders them live.

Multiple sinks can be attached. `EventLog.append` fans out to all of
them.


### Renderer

The renderer turns an `Event` into a `summary` string for the LogEntry
and into the longer narration the end-of-game transcript uses. It is the
only component that knows how to phrase events for humans.

It exposes two levels:

- `summarise(event) -> str`
  One-line summary used in the LogEntry. Examples:
  - "First Night: Setup completed (8 players, 5 Townsfolk + 1 Outsider
    + 1 Minion + 1 Demon)."
  - "Imp chose Alice — Alice died."
  - "Monk chose Bob — Bob is safe tonight."
  - "Fortune Teller chose Charlie and Dave — learned 'no'."
  - "Empath learned 1."
  - "Day 2: Eve nominated Frank. Frank received 4 votes (50% of alive).
    Frank was executed."
  - "Saint executed — game over, evil wins."
- `narrate(entries) -> Iterable[str]`
  A pass over a slice of the log producing the multi-paragraph end-of-game
  transcript. Groups by phase, omits redundant rows (every Wakeup that
  produced an Information line is collapsed into the Information line),
  and adds bridging narration ("On the second night, ...").

The renderer must never invent state. If a row in the log doesn't say
*how* a player died, the narration says "died". The renderer's
correctness is testable in isolation by feeding it canned LogEntry
sequences.


### Snapshot

To support fast rewind, `snapshot.py` periodically captures a full
game-state snapshot to a parallel store keyed by event index. Snapshots
are taken at every phase boundary (NightStart, NightEnd, DayStart,
DayEnd). To rewind to event N:

1. Find the latest snapshot at or before N.
2. Restore the engine's game state from that snapshot.
3. Replay log entries from snapshot index to N (re-applying their state
   mutations through the engine, but not their Prompts).
4. Truncate the log after N.

The snapshot store is in memory by default and can be backed by disk
when JsonlSink is enabled.


### Replay

`replay.py` provides a way to take a stored JSONL log and reconstruct
the entire game in a fresh engine instance. This is for:

- **Debugging.** Reproduce a bug from a recorded game.
- **Demo.** Walk new Storytellers through a sample game.
- **Tests.** Golden-file tests assert that a fixed sequence of
  Storyteller decisions produces a fixed log.

Replay does not re-run prompts. It feeds the recorded events back to
the engine, which applies their state mutations directly. This is what
makes the log + seating + decisions a complete record.


## What gets logged

The engine annotates each Event with a "loggable" hint when it is
emitted. The logger trusts the hint. The rules are:

| Event type            | Logged?                              | Visibility   |
|-----------------------|--------------------------------------|--------------|
| Setup                 | yes                                  | Storyteller  |
| NightStart / NightEnd | yes (phase markers)                  | Public       |
| DayStart / DayEnd     | yes (phase markers)                  | Public       |
| CheckCondition        | only if it gated something visible   | Storyteller  |
| Wakeup                | rolled into the resulting Info / Resolution row; not its own row |  |
| Select                | yes (records the player's choice)    | Storyteller  |
| Information           | yes (records what was shown, including false info if drunk/poisoned) | Storyteller |
| Resolution            | yes if it changed state              | Storyteller  |
| Death                 | yes                                  | Public       |
| Resurrect             | yes                                  | Public       |
| Drunken / Poisoned    | yes (toggle on and toggle off)       | Storyteller  |
| ChangeCharacter       | yes                                  | Storyteller  |
| ChangeAlignment       | yes                                  | Storyteller  |
| Nomination            | yes                                  | Public       |
| Vote                  | yes (final tally only, not per-hand) | Public       |
| Execution             | yes                                  | Public       |
| GameOver              | yes                                  | Public       |

The "Storyteller / Public" split is what lets us produce a clean public
recap that respects the rule "secrets are secret". A drunk Empath's
false `1` is logged as Storyteller-visible; the public recap does not
mention it.


## Drunk and poisoned: what we record

When a Player's ability fires while they are drunk or poisoned, the
engine emits two related rows:

1. The Information event the player actually saw on their phone (the
   *false* info), tagged with `source_state = drunk_or_poisoned` so the
   renderer can phrase it correctly: "Empath (drunk) was shown 0."
2. Optionally a paired "true" entry the engine knows but didn't surface
   to the phone, tagged with `visibility = STORYTELLER` and
   `kind = WOULD_HAVE_BEEN`: "Empath would have learned 2."

Both rows let the end-of-game transcript explain the gap between what
the player believed and what was true.


## Integration with the engine

The engine creates one `EventLog` at game start and passes it into the
event loop. The loop's contract:

```
for event in queue:
    if event.changes_state or event.is_phase_marker or event.is_visible:
        log.append(event, phase=engine.phase, visibility=event.visibility)
    for character in alive_characters:
        character.reaction(event, engine)
```

`Character.reaction` does not log anything. If a reaction emits a new
event (Imp Resolution -> Death), the engine logs the new event in turn.
This keeps logging centralised in one place.


## Integration with the UI

The Local UI subscribes to the StreamSink. Every appended entry pushes
a row to the timeline panel. Tapping a row jumps the UI's seat-state
view to "as of this entry", which is implemented by replaying from the
nearest snapshot.

The Mobile UI does not subscribe to anything in the logger. Player
phones see only the Information events the engine routes to them
through Prompts.


## Format

JSONL is the on-disk format. One LogEntry per line:

```
{"index": 0, "ts": 1714000000.001, "phase": "SETUP",
 "event": {"type": "SETUP", "source": null, "targets": [],
           "payload": {"players": [...], "characters_in_play": [...]}},
 "summary": "Setup completed.",
 "visibility": "STORYTELLER"}
{"index": 1, "ts": 1714000003.214, "phase": "FIRST_NIGHT",
 "event": {"type": "INFORMATION", "source": "Washerwoman:Alice",
           "targets": ["Bob","Carol"],
           "payload": {"shown_character": "Chef"}},
 "summary": "Washerwoman: shown that one of {Bob, Carol} is the Chef.",
 "visibility": "STORYTELLER"}
...
```

Field names match the engine's Event schema so a consumer can deserialise
straight back into Events. The renderer's `summary` is denormalised onto
each row so a reader (or the UI) does not need the engine code to render
the timeline.


## What the logger does *not* do

- It does not enforce rules. The engine decides whether an Event is
  legal; the logger only records what happened.
- It does not own game state. State lives on Players and Characters.
  The snapshot store is a derived view captured for rewind.
- It does not communicate with player phones. That is the UI's job.
- It does not edit history. Rewind truncates; corrections append. There
  is no in-place mutation of past entries.
